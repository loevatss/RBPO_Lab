# ЛР 5. JWT Access/Refresh и управление сессиями

## 1. Регистрация (опционально)

Если пользователя ещё нет:

```bash
curl -i -X POST 'http://localhost:8080/api/auth/register' \
	-H 'Content-Type: application/json' \
	-d '{"login":"user55","password":"Strong!Pass55"}'
```

## 2. Сценарий проверки (Шаги 1–5 из ТЗ)

Ниже используется формат `Authorization: Bearer <accessToken>`.

### Шаг 1. Вызвать POST /api/auth/login и получить access + refresh

```bash
curl -i -X POST 'http://localhost:8080/api/auth/login' \
	-H 'Content-Type: application/json' \
	-d '{"login":"user1","password":"Strong!Pass1","deviceId":"curl"}'
```

Скопируйте токены в переменные (любым удобным способом):

```bash
ACCESS_TOKEN='<вставьте accessToken>'
REFRESH_TOKEN='<вставьте refreshToken>'
```

### Шаг 2. С access-токеном обратиться к защищённому эндпоинту

Пример защищённого endpoint:

```bash
curl -i -X GET 'http://localhost:8080/api/posts' \
	-H "Authorization: Bearer ${ACCESS_TOKEN}"
```

### Шаг 3. Вызвать POST /api/auth/refresh и получить новую пару

Сохраняем старый refresh (нужен для шага 4):

```bash
OLD_REFRESH_TOKEN="$REFRESH_TOKEN"
```

Делаем refresh:

```bash
curl -i -X POST 'http://localhost:8080/api/auth/refresh' \
	-H 'Content-Type: application/json' \
	-d '{"refreshToken":"'"${REFRESH_TOKEN}"'"}'
```

Скопируйте новую пару токенов в переменные:

```bash
ACCESS_TOKEN='<новый accessToken>'
REFRESH_TOKEN='<новый refreshToken>'
```

### Шаг 4. Повторно вызвать /api/auth/refresh со старым refresh и убедиться в ошибке

Ожидаем `401` или `403` (в реализации: обычно `403`, т.к. это reuse-detection):

```bash
curl -i -X POST 'http://localhost:8080/api/auth/refresh' \
	-H 'Content-Type: application/json' \
	-d '{"refreshToken":"'"${OLD_REFRESH_TOKEN}"'"}'
```

### Шаг 5. Проверить статусы сессий в БД

Логика статусов:

- при `login` создаётся запись `user_sessions` со статусом `ACTIVE`;
- при первом `refresh` старая сессия становится `USED`, создаётся новая `ACTIVE`;
- при повторном `refresh` со старым refresh-токеном сессия помечается `REVOKED` и выдаётся ошибка.

Проверка статусов выполняется запросом в БД (так как это требование именно про БД, а не про HTTP).

Пример SQL (имя пользователя подставьте своё):

```sql
SELECT id, user_login, status, refresh_token_expiry
FROM user_sessions
WHERE user_login = 'user1'
ORDER BY refresh_token_expiry DESC;
```

## 3. Примеры вызовов CRUD с JWT

### Пример POST (без CSRF, только Bearer)

```bash
curl -i -X POST 'http://localhost:8080/api/posts' \
	-H 'Content-Type: application/json' \
	-H "Authorization: Bearer ${ACCESS_TOKEN}" \
	-d '{"userId":1,"text":"Hello from JWT"}'
```

### Пример admin-only endpoint

Нужно залогиниться под админом и использовать его `accessToken`:

```bash
curl -i -X POST 'http://localhost:8080/api/auth/login' \
	-H 'Content-Type: application/json' \
	-d '{"login":"admin1","password":"Strong!Pass2","deviceId":"curl"}'
```

Далее (с accessToken админа):

```bash
curl -i -X GET 'http://localhost:8080/api/users' \
	-H "Authorization: Bearer ${ACCESS_TOKEN}"
```
